# Three-minute demo runbook

Audience: hackathon judges and technical reviewers. The goal is to show one ambiguous
investigation, one controller improvement that passes declared gates, and one clearly rejected
candidate — without conflating the studies or overstating what the system knows.

Rehearsal status: the API requests and evidence below were verified by HTTP and tests, but the
click path has **not** been run in a browser in this environment. Do one browser rehearsal before
presenting. Every robot experiment is simulated; no live Meta Muse call is used.

## Before the clock starts

1. Start the API: `.venv/bin/python -m nautilus_api.server 8000`
2. Start the UI: `cd frontend && npm run dev` and open `http://127.0.0.1:3000/`.
3. Check that no `NAUTILUS_MUSE_ENABLED` value is set. The demo must not spend credits.
4. Confirm the four chips in the execution-mode legend are visible under the navigation.
5. Keep the browser at normal zoom, 1280 px wide or larger. Open one spare tab for evidence.
6. Have the fallback ready: if the API is down, stop the live claims and show the retained
   evidence JSON files only. Do not present recorded files as live computation.

## 0:00–0:20 — Frame the claim

Say: “Nautilus is an evidence workspace for simulated marine-robot failures. It separates what
was recorded, what is computed now, and what a model merely proposed. Today: one ambiguous
case, one accepted controller, one rejected controller.”

Point at the legend. Say: “Case A and B are live deterministic simulation. Case C is a recorded
development study. None is a live model call, and none is a physical robot run.”

## 0:20–1:00 — Case A: the evidence does not choose

The three Case Files cards are on **Overview**.

1. Read the Case A headline: “No cause selected · three explanations stay competitive.”
2. Click **Run case A now**. The button disables while the request runs.
3. The app lands on **Workspace → Simulation Lab**.
4. Point to **Diagnosis: ambiguous**, **Selected: none (abstained)** and the competitive list:
   `nominal`, `lateral_current`, `starboard_degradation`.

Say: “A −0.06 m/s lateral current is injected. Five declared explanations fit; the best score
gap is inside a frozen ambiguity threshold, so the passive protocol abstains. It does not know
the cause, and it does not pretend to.”

Then click the browser back button or **Overview**. In the Case A card click
**Show evidence · Passive fits & protocol**. Point to `kind: ambiguous`, `selected: null`, the
protocol fingerprint and the warning that scores are heuristic.

Say explicitly: “This is passive-protocol ambiguity, not an agent or Muse abstention. An active
probe on this same scenario resolves the current, which is why we do not claim the agent gave
up.”

## 1:00–2:10 — Case B: a bounded controller change

1. On **Overview**, in Case B click **Open Policy Studio**.
2. Click **Load example revision**. The diff should show integral gain and integral limit.
3. Click **Validate**. Expect a valid policy; no trial has run yet.
4. Click **Run paired trial (free)**. Wait for the 8-gate result.
5. Point to **Outcome: Recommended**, **Mean RMS change −0.58 m**, and **8/8** gates.
6. Point to the per-scenario rows: nominal RMS rises 0.002 → 0.011 m, still inside the 0.1 m
   regression gate; the current scenario improves 1.986 → 0.809 m and corridor excursions fall
   from 79.3% to 0%.
7. Click **Held-out robustness**. Expect the `Recommended` label to hold on the held-out split;
   the mean improvement there is 0.493 m.
8. Click **Export engineering report**, then open **Reports** in the top navigation to show the
   downloadable artifact.

Say: “The candidate is baseline plus bounded integral compensation, proposed by the host
example, not by Muse. Baseline and candidate see identical scenarios, seeds and noise. It passed
eight predeclared gates on development and still improved on the held-out split. This is a
simulation result, not a repair or a safety certificate.”

Back on **Overview**, open **Show evidence · Paired trial (8 gates)** and point to the trial
fingerprint `585bd1d5…`, gates, rows and traces. Mention that a repeat produced the same
fingerprint.

## 2:10–2:40 — Case C: a rejected candidate

1. On **Overview**, read Case C: “Rejected 14 m lookahead · RMS 5.02 m vs 2.68 m baseline.”
2. Click **Show evidence · Recorded comparison**.
3. Point to the three scenario rows and the fingerprints: candidate `9769d71b…`, baseline
   `adda0ae6…`, 3 m alternative `3add7582…`.

Say: “This candidate was predeclared before execution. On all three retained development
scenarios it is worse than the 7 m baseline — 5.02 m versus 2.68 m RMS on the first. This is a
recorded artifact, not recomputed today, and its scenario inputs are private. It was not
selected or generated by Muse.”

Then say the separation line: “The 3 m lookahead candidate in this study is not the Case B
bounded-integral policy. They are different controller studies and we do not merge their
numbers.”

## Optional Muse segment (recorded, not live)

Only if time allows, and only after Case B. On **Overview**, open the **Recorded Real Muse** card.

Say: “This is a recorded real Meta Muse session from development. It shows one controller
study: Muse proposed a parameter change, and the host’s gates decided. It is a recording, not a
live call, and it did not generate structural source code.”

Do not say Muse picked the controller, that Muse can accept its own proposal, or that the
recording is a live run. Structural source generation is not verified and must not be shown.

## 2:40–3:00 — Limits and close

Say: “The passive scores are heuristics, not probabilities. Hidden plant truth never reaches
the lab UI. Case A is passive ambiguity, Case B is a two-scenario development split plus three
held-out scenarios, and Case C cannot be regenerated from the public tree. The 3D viewer replays
recorded telemetry only; live runs are shown numerically because public telemetry has no
x-position. Meta Muse is server-side and off by default. The upgrade path keeps every model
action behind validated tools and host-side numerical checks.”

Stop. Do not add unverified claims or extra cases.

## If something fails

| Symptom | Response |
|---|---|
| Case A button disabled | API is not enabled for this build. Say so, do not fake a run; show the evidence file and the HTTP result in `docs/EVALUATION.md`. |
| Simulation request errors | Keep the error visible, state that the live path is unavailable, and switch to the retained artifacts. |
| Paired trial fails a gate | Report the actual failed gate; do not call it Recommended or hide the result. |
| Held-out robustness differs | Report the held-out outcome as shown; the demo’s claim is conditional on the trial that ran. |
| Evidence file 404 | Check that the app is served from the frontend root; open `/evidence/…` directly. |
| No 3D scene | Expected unless a recorded visualization companion is imported. Do not claim a live 3D replay. |

## What not to say

- Do not call Case A “the agent abstained” or “Muse abstained.”
- Do not call Case B “fixed,” “safe,” “benchmarked,” or “Muse-generated.”
- Do not call Case C “Muse-rejected.”
- Do not merge the 3 m lookahead study with the bounded-integral policy.
- Do not describe the 14 m study as held-out or as a parameter search.
- Do not present a mock session as evidence.
